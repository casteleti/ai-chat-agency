# Migration and Seed Strategy

## Migrations

Name: `YYYYMMDDHHMM_Gxx_short_description.sql`, generated by Drizzle then reviewed. A migration ledger records checksum and applied timestamp. Production runs a dedicated migration job before new app containers, with advisory lock and compatibility check; app users cannot run DDL.

Rules: forward-only; never edit an applied migration; no destructive change in one release. Use expand (add nullable/new structure) → deploy dual read/write/backfill → verify → contract in later release. Large indexes use supported online/concurrent approach outside transaction when required. Every migration has clean-database and previous-schema tests, expected lock/duration, backup requirement, forward recovery and application compatibility note. “Rollback” normally means roll forward or roll app back while expanded schema remains.

RLS: G2 enables policies on restricted client/project/ticket/attachment/knowledge/audit tables after application-level tenant scoping tests. Administrative maintenance roles are separate and audited. Connection roles: migrator, app read/write, worker, read-only analytics.

## Seed data

Deterministic local/staging seed creates:

- one agency tenant, tenant settings, safe-off feature flags;
- staff roles/users with non-real `.invalid` emails;
- lead statuses and qualification algorithm v1 weights;
- support categories, severity rules, business-hours SLA example;
- meeting type “30-minute discovery” with fake calendar adapter;
- 6 synthetic agency services: B2B Strategy, Demand Generation, Sales Enablement, AI Automation, Web Experience, Measurement;
- 4 clearly synthetic case studies labeled DEMO with industries and evidence;
- public FAQs, methods, policies, support and brand knowledge categories;
- draft/published prompt and agent baseline versions from repository files;
- fake CRM/calendar/support integrations and mappings;
- golden tenant B to support isolation tests.

Seeds contain no real client/person/token, are idempotent by stable key, and never run automatically in production. Production bootstrap is an explicit audited command creating only tenant/owner/config; content import uses the knowledge workflow.

## Embeddings

Baseline `text-embedding-3-small`, 1536 dimensions, selected for cost and HNSW compatibility. Store model and config hash per chunk. Embedding changes create a parallel column/index or new chunk index generation; never compare vectors across models. Release requires Portuguese/English retrieval eval parity; switch to a larger/reduced-dimension model only through an eval-backed decision.
