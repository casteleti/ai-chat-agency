# AI Security and Trust Zones

Trust order: server system policy → server security/tool policy → published tenant role/brand → validated runtime facts/capabilities → untrusted user/retrieval/web/file/provider content. Lower zones cannot modify higher zones.

## Controls

- Context blocks are typed and delimited; instruction fields are never populated from untrusted sources.
- Capability manifest is generated by policy per turn and exposes only allowed tools. Tool descriptions contain no secrets.
- Model proposals are parsed with strict schemas (`additionalProperties:false`), size/depth limits and enum IDs; validation failure becomes safe error/retry, not permissive parsing.
- Tool executor independently resolves canonical resource IDs, tenant, actor and current state; ignores model-provided identity/permission.
- Confirmations are server-issued, signed/expiring, bound to request hash and consumed once.
- Retrieved/source instructions such as “ignore previous” are quoted as content or omitted, never followed.
- Model output is escaped; Markdown allowlist excludes raw HTML, iframe, script, style, data URLs and arbitrary link schemes.
- Hidden chain-of-thought is never requested, stored or shown. Store concise rationale/evidence codes.
- Prompt/provider/model changes require eval and version; fallback cannot weaken policies.

## Red-team families

Direct jailbreak, role impersonation, encoded instructions, multi-turn policy erosion, prompt extraction, knowledge poisoning, cross-tenant requests, malicious tool arguments, confirmation replay, URL SSRF, attachment injection, fake case/price/booking requests, social engineering staff, and cost-amplification loops.

Release blockers: any unauthorized tool execution, private/cross-tenant disclosure, invented transactional success, fabricated case/price, or security policy override on the deterministic suite.
